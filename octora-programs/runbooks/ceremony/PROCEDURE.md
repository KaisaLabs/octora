# Trusted setup ceremony — Octora withdraw circuit (P0-2)

**Status:** Authoritative procedure for the multi-party Powers-of-Tau ceremony that produces the mainnet `withdraw.zkey` + verifying key.
**Last updated:** 2026-05-10.
**Owner:** Engineering lead, in coordination with at least three independent contributors.

## Why this matters

The audit (`runbooks/PRODUCTION_READINESS.md` P0-2) is unambiguous: a Groth16 mixer whose `.zkey` was generated by a single party puts that party in possession of the **trapdoor** — they can mint counterfeit withdrawal proofs at will and drain the entire pool. The fix is a multi-party ceremony where at least one honest contributor's randomness is enough to make the trapdoor unrecoverable.

The legacy `octora-api/src/modules/vault/circuits/setup.sh` runs a single-contributor ceremony with `--entropy="octora-devnet-mvp-$(date +%s)"`. That script is fine for **devnet** — the ceremony output is throwaway and explicitly marked as such. For mainnet, every step in this runbook is mandatory.

## Pre-requisites

- The circuit source (`octora-api/src/modules/vault/circuits/withdraw.circom`) has been frozen for the mainnet release. The constraint count is final; any further edit forces a re-ceremony.
- `circom 2.1.x` and `snarkjs` are pinned to the same versions every contributor uses.
- A **community Powers of Tau** transcript at power 16 or higher exists. The Hermez `pot16_final.ptau` from the public PSE ceremony is acceptable — it has hundreds of independent contributions and a published transcript.
- At least **three independent contributors**, each on different hardware in different physical locations, with no shared admin tooling between them. One on a laptop, one on an air-gapped machine, one in a cloud sandbox is a fine spread.
- Each contributor knows how to publish a SHA-256 hash on a public channel they control (Twitter/X account, GitHub gist signed with a personal GPG key, on-chain memo from a long-lived wallet).
- The repo's `withdraw.circom` matches the SHA-256 baked into the ceremony coordinator's invitation. Mismatches abort the ceremony.

## High-level shape

```
Phase 1 (Powers of Tau) — universal, reuse community transcript
        │
        ▼
Phase 2 (circuit-specific) — runs on this circuit's R1CS
        │
        ▼  ≥3 independent contributors, each adds entropy
        ▼
Final zkey ──→ verification_key.json ──→ groth16.rs vk bytes
        │
        ▼
On-chain program references the new vk
```

## 0. Coordinator setup (the engineering lead)

1. Tag the source.
   ```bash
   git tag -s ceremony-withdraw-mainnet-v1 -m "Frozen for trusted setup"
   git push --tags
   ```
2. Compute the canonical hash of the circuit source.
   ```bash
   sha256sum octora-api/src/modules/vault/circuits/withdraw.circom
   ```
   Publish that hash inside the ceremony invitation. Every contributor verifies they're working from the same circuit.
3. Compile the circuit ONCE on a clean machine. The R1CS is what every contributor will hash against; if its `.r1cs` SHA differs from the coordinator's, the contribution is rejected.
   ```bash
   cd octora-api
   pnpm install
   bash src/modules/vault/circuits/setup.sh   # devnet path; we'll override outputs below
   sha256sum src/modules/vault/circuits/build/withdraw.r1cs
   ```
4. Download a community phase-1 transcript at sufficient power. For our 20-level Merkle circuit, phase-1 power 16 is enough (~2¹⁶ constraints). Pin a known-good source:
   ```bash
   curl -L -o pot16_final.ptau \
     https://hermez.s3-eu-west-1.amazonaws.com/powersOfTau28_hez_final_16.ptau
   sha256sum pot16_final.ptau
   ```
   Confirm the SHA matches the value published by the PSE ceremony coordinator.
5. Generate the **initial** circuit-specific zkey. This is the seed everybody else builds on.
   ```bash
   pnpm exec snarkjs groth16 setup \
     src/modules/vault/circuits/build/withdraw.r1cs \
     pot16_final.ptau \
     ceremony/withdraw_0000.zkey
   ```
6. Publish the SHA of `withdraw_0000.zkey` and ship the file to **contributor A** via a channel that's both authenticated and tamper-evident (Keybase/Signal + GPG-signed gist URL).

## 1. Per-contributor procedure

Each contributor (A, B, C, ...) does the following on their independent machine. They MUST NOT share their entropy, and they MUST verify the previous contribution before adding their own.

### 1a. Verify the upstream

```bash
sha256sum withdraw_<n>.zkey
# Compare to the SHA the previous contributor published.

pnpm exec snarkjs zkey verify \
  build/withdraw.r1cs \
  pot16_final.ptau \
  withdraw_<n>.zkey
# Output must end with "ZKey Ok!"
```

If verify fails, stop. Do not contribute on top of an unverifiable zkey — the chain integrity is gone.

### 1b. Contribute

Generate fresh entropy from a source the contributor controls. Examples:

- A keyboard mash (≥ 256 chars).
- `head -c 64 /dev/urandom | base64`.
- A coin-flip transcript (literally).

Use it in `zkey contribute`:

```bash
pnpm exec snarkjs zkey contribute \
  withdraw_<n>.zkey \
  withdraw_<n+1>.zkey \
  --name="contributor-<initials>-YYYY-MM-DD" \
  --entropy="<the entropy string>"
```

`snarkjs` mixes that entropy with `crypto.randomBytes` from the host. Both must be present; passing only `--entropy` is fine because the host RNG is also pulled in.

### 1c. Attest

Each contribution produces a hash the contributor MUST publish in a way that ties their name to that hash:

```bash
sha256sum withdraw_<n+1>.zkey
```

Acceptable publication channels:

- A signed message on Twitter/X from a multi-year-old account that the team can verify.
- A GitHub gist signed with the contributor's GPG key.
- An on-chain memo tx from a wallet the contributor has used for years.

Two of the three is even better. The point: anybody can re-derive the SHA from the published `.zkey` and confirm the contributor stood behind it.

### 1d. Hand-off

Send `withdraw_<n+1>.zkey` to the next contributor (or to the coordinator if you're the last). Authenticated channel only — Signal, Keybase, or a TLS-fronted endpoint with a published cert pin. **Never** send via plain email.

## 2. Coordinator — finalize the zkey

After the last contributor (call them N), the coordinator does:

```bash
# Verify the full chain.
pnpm exec snarkjs zkey verify \
  build/withdraw.r1cs \
  pot16_final.ptau \
  withdraw_<N>.zkey

# Apply a "beacon" — a public, unpredictable randomness source like a
# block hash from a future Bitcoin block, or the VDF output of a known
# post-ceremony future event. snarkjs requires a hex string.
BEACON=$(curl -s "https://blockstream.info/api/blocks/tip/hash")
pnpm exec snarkjs zkey beacon \
  withdraw_<N>.zkey \
  withdraw_final.zkey \
  "$BEACON" 10 \
  --name="ceremony-beacon-$(date -u +%Y%m%dT%H%M%SZ)"

# Re-verify the final zkey.
pnpm exec snarkjs zkey verify \
  build/withdraw.r1cs \
  pot16_final.ptau \
  withdraw_final.zkey
```

The beacon ensures even if every named contributor colluded, the final randomness is not under any party's control. Document the beacon source and value in the transcript.

## 3. Generate the verifying key

```bash
pnpm exec snarkjs zkey export verificationkey \
  withdraw_final.zkey \
  verification_key.json
```

Cross-check the public-input count:

```bash
jq '.nPublic' verification_key.json
# Must be 5 — root, nullifierHash, recipient, relayer, fee.
```

## 4. Regenerate the on-chain verifier bytes

The verifying key is consumed by `programs/octora-mixer/src/verifier/groth16.rs` as compiled-in byte arrays:

```bash
node scripts/convert-vk-to-rust.mjs \
  octora-api/src/modules/vault/circuits/verification_key.json \
  > programs/octora-mixer/src/verifier/groth16.rs
```

Diff the result. The byte arrays for `VK_ALPHA`, `VK_BETA`, `VK_GAMMA`, `VK_DELTA`, and `VK_IC` will all change. The program ID, public-input count, and helpers do NOT change.

Re-run the program tests to confirm the new vk verifies a freshly-generated proof end-to-end:

```bash
cd octora-api
pnpm exec tsx scripts/init-mixer-pool.ts --localnet
pnpm exec vitest src/modules/vault/__tests__
```

If the on-chain verifier rejects a freshly-generated proof, the vk export is wrong (most often: byte-order or compression flag). Fix `convert-vk-to-rust.mjs` and rerun.

## 5. Publish the transcript

Create `runbooks/ceremony/transcript-mainnet-v1/`:

```
runbooks/ceremony/transcript-mainnet-v1/
├── README.md                  # Summary + table of contributors
├── circuit.r1cs.sha256        # Hash the contributors checked against
├── pot16_final.ptau.sha256    # Phase-1 transcript hash
├── withdraw_0000.zkey.sha256  # Coordinator init
├── withdraw_0001.zkey.sha256  # Contributor A
├── withdraw_0002.zkey.sha256  # Contributor B
├── withdraw_0003.zkey.sha256  # Contributor C
├── withdraw_final.zkey.sha256 # After beacon
├── verification_key.json
├── beacon.txt                 # Beacon source + value
└── attestations/              # Per-contributor signed statements
    ├── A.sig
    ├── B.sig
    └── C.sig
```

Commit the directory. Update `runbooks/PRIVACY_MODEL.md` to point at this transcript as the trust anchor.

## 6. Final zkey distribution

The `.zkey` is **public** — clients need it to prove. Ship it via the same channel that already serves the wasm prover (`octora-web` static assets, ideally with SRI). Pin its SHA in the docs.

Do **NOT** delete intermediate contributor zkeys. They are the evidence that the chain is sound; if someone questions whether contributor B was honest, you must be able to point at `withdraw_0001.zkey` (their input) and `withdraw_0002.zkey` (their output) and have anyone re-run `zkey verify`.

## 7. Mainnet readiness gates after the ceremony

- [ ] `verification_key.json` committed.
- [ ] `programs/octora-mixer/src/verifier/groth16.rs` regenerated and unit tests green.
- [ ] `withdraw.zkey` published at a stable URL with SHA pinning.
- [ ] Transcript directory pushed to `main`.
- [ ] `runbooks/PRIVACY_MODEL.md` updated to reference the transcript.

Only then is the launch sequence (`runbooks/deployment/MAINNET.md`) cleared to run.

## What "compromise" looks like

The trusted setup is sound iff at least one contributor was honest AND the coordinator did not tamper with hand-offs. Failure modes that compromise the ceremony:

- All contributors collude. Mitigated by picking contributors with no business relationship and publishing the contributor list in advance.
- The coordinator silently substitutes a zkey before publishing. Mitigated by every contributor's published SHA — anyone can fetch the zkey from the published URL, re-hash, and confirm.
- A contributor's machine is compromised. Mitigated by N contributors — even one honest contributor whose machine wasn't compromised destroys the trapdoor.

If a compromise is suspected post-launch, the only recovery is **a second ceremony** + a program upgrade to the new vk. There is no patching a compromised trusted setup in place.
