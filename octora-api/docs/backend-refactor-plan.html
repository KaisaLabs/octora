Octora API · Backend Refactor Plan

Standardize, clean up, and scale the Octora backend

The codebase is production-ready for beta — Fastify + Prisma + repository pattern, strict TS, wallet auth, recovery worker, real health/metrics. The goal of this plan is to consolidate inconsistencies that have crept in (error handling, validation, config), decompose the 1k-LOC services that hide complexity, and remove the in-memory shortcuts that won't survive a horizontal scale-out (rate limiter, beta-cap aggregation).

2. Refactor principles

One way to do each thing. One error base class. One validation library. One config module. One response envelope. Inconsistency is the bug, not the second pattern.
Boundaries enforce themselves. If process.env is only read in config.ts, drift can't happen. If Prisma is only imported in *.repository.ts, services stay pure.
Decompose by axis of change. Split executor.service.ts not by line count but by what changes together: pool setup, token minting, tx building, liquidity math.
SQL beats JS. Aggregations, counts, sums go to Postgres. The Node process should not loop over rows it could have SUM()'d.
Stateless processes. Anything that lives in a Map in memory (rate limits, caches, anonymity-set state) needs a story for >1 instance — even if today the answer is "single instance, will move to Redis at X RPS".
No new feature work in this refactor. If a task changes behavior, it's out of scope. Diffs should be reviewable as pure structure changes.

4. Phased plan

Phase 0Foundation: errors, validation, config~3 days

Land the primitives the rest of the refactor depends on. Every later phase assumes these exist.

  • P0 Introduce ApiError base class with statusCode, code (string enum), details. Subclasses: NotFoundError, ConflictError, ValidationError, UnauthorizedError, RateLimitedError, UpstreamError. Replaces ad-hoc Error + string matching in controllers. Global setErrorHandler formats response from err instanceof ApiError.
  • P0 Migrate existing custom errors (PositionNotFoundError, AnonymitySetTooThinError, JupiterPriceError, MeteoraApiError) to extend ApiError. Backwards-compatible — same names, just a parent. Controller branches collapse to one handler.
  • P1 Add zod for request validation. Bridge to Fastify schema via zodToJsonSchema so OpenAPI/Scalar still works. BigInt strings, base58 pubkeys, denomination enums all get one place to live. Failed parses become ValidationError automatically.
  • P1 Re-implement config.ts as a zod schema + parsers.ts helpers (parseCsv, parseBigIntList, parseBoolean, parseUrlList). Replaces the 83-LOC ad-hoc parsing block. loadMixerDenominations / loadFrontendUrl / loadMixerRelayerConfig become declarative.
  • P1 Lint rule (eslint no-restricted-syntax) banning process.env outside common/config/. Makes the boundary self-enforcing. Catches the mixer.service.ts:41 drift mechanically.
  • P2 Standard response envelope: { data: T } on success, { error: { code, message, details? } } on failure. Codify in http/envelope.ts. Frontend can pattern-match one shape. Today every endpoint returns its own structure.
Phase 1Module standardization~4 days

Every modules/<name>/ follows the same template. Touching a new module should require zero file-system orientation.

  • P1 Adopt the canonical 6-file module template (routes, controller, service, repository, schemas, types). Refactor each module to fit; collapse stragglers into __internal/. Today some modules have controller.ts, others stuff handlers in routes.ts. One template makes search-by-convention work.
  • P1 Move every Prisma call into *.repository.ts. Lint-ban @prisma/client imports outside repositories & common/db/. Already 90% there — this finishes the boundary.
  • P1 Extract testWalletStamper() and the options.prisma === undefined branch out of position.routes.ts. Move to test-kit/route-harness.ts; tests build their own app. Production code shouldn't conditionally run on missing dependencies. Test paths in prod files are landmines.
  • P2 Generate shared types package (octora-api-types) from zod schemas. Frontend imports it instead of redeclaring. Today drift between FE/BE response shapes is silent. With zod → z.infer, the type is the schema is the validator.
  • P3 Replace console.* with app.log.* across 19 sites. Remove P0-20 / P1-30 audit-ticket comments — link to internal tracker once. Audit doc lives outside the repo and will rot. One SECURITY.md link in app.ts beats 50 inline references.
Phase 2Decompose the mega-services~5 days

Split the three 600+ LOC services along their natural seams. Files become greppable; concerns become testable in isolation.

  • P1 Split executor.service.ts (1,009 LOC) into builders/dlmm-pool.builder.ts, builders/token.factory.ts, builders/liquidity.planner.ts. executor.service.ts becomes the orchestrator (~150 LOC). Each builder testable with mocked Anchor program; today everything imports the world.
  • P1 Split dlmm.service.ts (896 LOC): dlmm.api.ts (Meteora HTTP client + circuit breaker), dlmm.chain.ts (chain-direct fallback), dlmm.service.ts (resolution policy: which source to use). The two source paths today share zero structure; consolidating the policy into one place makes adding a third source trivial.
  • P1 Split position.service.ts (728 LOC) by lifecycle stage: position.intent.service.ts, position.execution.service.ts, position.claim.service.ts. State-machine guard stays in domain/. Aligns to the state graph that already exists in domain/ — the service should mirror the model.
  • P2 Move recovery-worker.ts from modules/positions/ to top-level workers/. Workers depend on services, not the other way around. Today the worker is buried in the module that defines its target — circular when worker grows to handle other modules.
  • P2 Split test-kit/factories.ts (354 LOC) per domain: position.factory.ts, activity.factory.ts, walkthrough.factory.ts.
  • P2 Pull DLMM PROGRAM_ID and PRESET_PARAMETER into config (OCTORA_DLMM_PROGRAM_ID, OCTORA_DLMM_PRESET_PARAMETER) with mainnet defaults. Localnet/devnet/mainnet need different IDs. Hardcoding makes env switching a code change.
Phase 3Scalability: drop the in-memory shortcuts~5 days

Anything that prevents running >1 instance comes out. Postgres or Redis takes over.

  • P0 Replace sumActiveAmountSol() JS reduce with a Prisma aggregate({ _sum: { amount: true } }). Add a (state, walletAddress) partial index for state IN ('intent','executing','active'). O(1) round-trip vs O(n) memory. Becomes a non-issue at any scale.
  • P0 Define RateLimiter interface; ship two implementations: MemoryRateLimiter (current behavior) and RedisRateLimiter (token-bucket via SCRIPT). Wire selection from config. Single-instance today, multi-instance ready. Same API, swap at boot.
  • P0 Make rate limiter wallet-keyed in addition to IP. Composite key {wallet}:{route} when wallet is present, else {ip}:{route}. Audit P3 issue — coordinated abuse from one IP bypasses today's per-user limit.
  • P1 Add a generic CircuitBreaker wrapper for outbound HTTP (Meteora, Jupiter). Failures in N seconds open the breaker; half-open probe; close on success. A Jupiter outage today means every /prices call hangs until timeout. Breaker fails fast.
  • P1 Replace per-call Meteora fetches with a per-pool TTL cache (node-cache or lru-cache) keyed by pool address. Configurable TTL, currently effectively 5s. Same data is requested by every /dlmm/pools hit. Cache is already conceptually present — formalize it.
  • P2 Add missing indexes: PositionReconciliation(positionId), ExecutionSession(state, failureStage), Position(state, createdAt) for recovery-worker scans. Recovery worker scans by state + age every 30s. Without index, sequential scan grows with table size.
  • P2 Connection pool tuning: explicit Prisma datasource pool size; document PgBouncer mode (transaction vs session); add statement_timeout guard. Default Prisma pool is 2× CPU — hits limits early on Vercel-style cold starts.
Phase 4Observability & testing~4 days

Catch regressions from this refactor and make the next one cheaper.

  • P1 Per-route latency histograms in /metrics: http_request_duration_ms{route, status}. Already have JSON snapshot — add request timings. Today metrics are point-in-time totals; no way to spot a route degrading.
  • P1 Integration test layer: spin up Postgres + Fastify in beforeAll, hit real routes with real auth. One test per route happy-path + 401/403/422. Today's tests are unit-only at services. The contract surface is untested.
  • P2 Test the recovery worker against a fake RPC (sequence of getSignatureStatuses responses). Verify exact-once Sentry capture, idempotent state advance.
  • P2 Document Sentry activation in README (it's currently a dynamic import that nobody enables).
  • P2 Add OpenTelemetry traces (Fastify plugin) with span propagation through services → repos → outbound HTTP. When a slow request gets reported, "which downstream call" should be a graph lookup, not a code reading exercise.
Phase 5Long-term: queues & horizontal scale~when traffic justifies

Defer until usage demands it. Plan now so the move is mechanical.

  • P3 Move recovery worker to BullMQ (Redis) jobs. Each stuck position becomes a delayed job; retries / DLQ are free. Removes the "single-instance only" footnote on the API. Vercel-deployable.
  • P3 Materialize beta-cap aggregates as a Postgres view or trigger-maintained counter (position_caps table). Even with SUM(), sub-ms reads matter for a hot pre-write check.
  • P3 Read replica for analytics queries (/metrics, admin endpoints).

5. Migration discipline

Each phase ships in its own PR series, behind an integration test. No "while I'm in here" feature changes. If a phase breaks something, revert is one PR. The mega-services in particular get a "split is a no-op" PR (move code, keep public exports identical), then a second PR that simplifies callers.

Risk register

RiskMitigation
Error envelope change breaks frontendShip Phase 0 envelope behind a per-route opt-in flag; flip routes one at a time after FE updates.
zod migration drops a validation caseKeep both validators in parallel for one release; log when zod accepts but JSONSchema would have rejected (and vice versa).

6. Definition of done

Standardization

  • One error base class; controllers contain zero if (err.message.includes(...)).
  • One validator (zod). Same schemas drive OpenAPI and runtime.
  • One config module. process.env grep returns only common/config/.
  • Every module follows the 6-file template.

Cleanliness

  • No file over 500 LOC in modules/.
  • No test branches in production routes.
  • No console.* in src/.
  • Zero hardcoded program IDs / magic constants outside config.

Scalability

  • Beta-cap check is a single SQL aggregate.
  • Rate limiter has a Redis impl; wallet-keyed when wallet present.
  • All outbound HTTP wrapped in circuit breaker.
  • All recovery-worker scan paths covered by an index.

Observability

  • Per-route latency histograms exposed.
  • Integration tests cover every route's happy + auth-fail path.
  • Recovery worker has a deterministic test against a fake RPC.

7. Sequencing

Phases are mostly parallelizable after Phase 0. Recommended order if one person: 0 → 1 → 3 (P0 only) → 2 → 3 (rest) → 4 → 5. The P0 items in Phase 3 (aggregation, rate limiter) jump the queue because they are surgical fixes that don't depend on the module decomposition.
