# Mid-position fee claim (no close)

**Status:** ready-for-agent
**Type:** enhancement
**Slice:** AFK

## What to build

Let a user claim accrued fees on an `active` Position without closing it. The atomic compound version of this (claim + re-deposit in one tx, residual stays in-position) is wontfix per dust/06 + ADR-0003 — Meteora's current DLMM ix surface forces fees through user token accounts on the way out. This ticket builds the *non-atomic* version instead: claim to stealth, accept that fees land in the Stealth Wallet's free balance, and let the user choose what to do with them.

Lower priority than tickets 01–04 — full close is the dominant exit pattern. Fee-claim is a "keep the position open and harvest" path mostly relevant for long-running positions.

## Flow

1. UI shows a Claim button on Position detail page when state is `active` AND accrued fees exceed a configurable display threshold
2. User clicks Claim
3. Optional disclosure: "Claimed fees will sit in your Stealth Wallet's free balance. Re-mixing or withdrawing requires a separate action." Lightweight, not load-bearing — no privacy hit beyond what closing already costs
4. Backend builds + relayer signs `dlmm_claim_fees` ix (single tx); stealth receives the claimed amounts
5. Position state stays `active` — no transition. Activity Record emitted recording the claim amount + signature
6. After the claim lands, UI shows: "Fees claimed to Stealth Wallet. {SOL amount} SOL + {OTHER amount} {OTHER mint}." With two follow-up actions:
   - **Re-mix** — if the SOL portion is at or above one Mixer Pool denomination, offer a one-click flow that deposits one denomination into the same Mixer Pool, producing a fresh Commitment. Reuses the deposit machinery from Flow 1.
   - **Leave it** — fees stay in stealth indefinitely. User can re-mix or full-close later.

Other-side residual on claim follows the same protocol-level-dust rule as close: it stays in the stealth, accepted (ADR-0003).

## Backend

- `POST /positions/:positionId/claim-fees` route + service. No state machine transition; just an Activity Record + an updated `accruedFees`/`claimedFees` projection on the Position
- Optional re-mix endpoint or reuse existing `mixer/deposit` flow with a `source: "fee-claim"` field on the Activity Record

## UI

- Claim button on Position detail; surfaces accrued fee preview (read from Meteora pool state)
- Post-claim status panel showing what landed in stealth + Re-mix / Leave-it actions
- Activity Record entry visible in the Position's activity log

## Token-2022 / TransferHook gating

Ticket 04 covers this for close. The same rule applies to fee-claim: if the other-side mint is blocked, the claim *itself* may work (no swap involved), but the user can't re-mix the other-side portion. Surface this as a tooltip on the post-claim panel rather than blocking the claim.

## Acceptance criteria

- [ ] `POST /positions/:positionId/claim-fees` route + service wired
- [ ] Claim button on Position detail page, disabled when accrued fees below display threshold
- [ ] Post-claim status panel shows received amounts + Re-mix / Leave-it actions
- [ ] Re-mix action reuses the existing Flow 1 deposit machinery and lands a fresh Commitment in the same-denomination Mixer Pool
- [ ] Position state remains `active` throughout claim + re-mix; no `Position` state-machine changes
- [ ] Activity Record entries record claim amounts + (if re-mixed) re-mix amount + new commitment leaf-index
- [ ] Tests: claim path lands on stealth balance; re-mix offer appears only when SOL portion ≥ denomination; re-mix actually deposits + emits the Activity Record
- [ ] No regression on full close (ticket 01)

## Out of scope

- Atomic compound `claim_fee → mixer.deposit` (wontfix per dust/06 + ADR-0003)
- Auto-compound / auto-re-mix UX (deferred until users ask for it)
- Token-2022 / TransferHook precheck for re-mix — surface as tooltip, don't block

## Blocked by

None — can start immediately. Reuses the existing Flow 1 deposit machinery.
