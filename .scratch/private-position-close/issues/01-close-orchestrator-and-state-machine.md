# Private Position Close orchestrator + state machine

**Status:** done
**Type:** enhancement
**Slice:** AFK

## What to build

The mainline implementation of Flow 3 (Private Position Close). End-to-end, an `active` Position can be closed privately: DLMM exit → conditional swap of any non-SOL pair side back to SOL → re-mix the SOL into the Mixer Pool as a fresh Commitment, leaving a new anonymity-set entry the user can withdraw later to a fresh recipient.

The privacy guarantee: a bot watching the chain sees the Stealth Wallet close its DLMM Position, swap any other-side tokens to SOL on Meteora, and re-deposit denominated SOL into the Mixer Pool. The connection between the original deposit and any future withdrawal stays inside the Mixer Pool's Merkle Tree.

**Orchestration sequence (relayer-signed, three serial transactions — not atomic):**

1. `dlmm_withdraw_close` — Executor CPI to Meteora: claim accrued fees + remove all liquidity from every bin in the Position's range + close the DLMM Position account. Output: stealth holds SOL + (optionally) the other-side token.
2. **Conditional `dlmm_swap`** — if the stealth's post-close balance of the other-side token exceeds a dust threshold (e.g. 1000 lamports of the other mint), swap to SOL via Meteora. Skipped if the other side is already SOL or if residual is below threshold.
3. `mixer.deposit` — relayer-signed deposit of one denomination worth of SOL into the same-denomination Mixer Pool the original deposit used. Produces a fresh Commitment that the user can later withdraw to a new recipient.

If the closed Position's total SOL value doesn't cleanly match a single denomination, denominate against the *original* Mixer Pool denomination and accept that the residual (sub-denom dust) stays in the stealth wallet. This residual is the documented protocol-level dust (see ADR-0003 and `.out-of-scope/sweeper.md`) and is not addressed by this ticket.

## State machine

Extends the existing `Position` `ExecutionState` union with the close-flow cluster. Reuse the same transitions table + guard pattern dust/03 established.

```
active
  ├─ → CLOSING                       (relayer submits dlmm_withdraw_close)
  │     └─ → CLOSE_FAILED            (terminal w/ recovery)
  │
  ├─ → SWAPPING                      (only if non-SOL residual > dust)
  │     └─ → SWAP_FAILED             (terminal w/ recovery)
  │
  ├─ → REMIXING                      (relayer submits mixer.deposit)
  │     └─ → REMIX_FAILED            (terminal w/ recovery)
  │
  └─ → CLOSED                        (terminal, success)
```

Failed states are terminal but recoverable via the user-signed close-recovery escape in ticket 03.

## Activity Records + Recovery Guidance

Add `recoveryCatalog` entries for each new Failure Stage: `close-submission`, `swap-submission`, `remix-submission`. Each entry should follow the existing pattern (headline, message, terminal flag, `safeNextStep`, optional `fallbackMode`). `surfaceDowngradeDisclosure` does **not** apply here — there's no Mode Fallback on the close path.

Activity Records emit on each transition.

## API

- `POST /positions/:positionId/close` — initiates the close. Validates state is `active`, kicks the orchestrator.
- The orchestrator records state transitions through the existing `Position` aggregate, not a parallel state machine.

## UI

- **Close button** on the Position detail page when state is `active`. Disabled in any other state.
- Progress indicator that reflects each of `CLOSING / SWAPPING / REMIXING` with appropriate labels (e.g. "Closing position on Meteora…", "Swapping {OTHER} → SOL…", "Re-mixing into anonymity set…").
- On any `*_FAILED` state, render the recovery panel (3-button pattern is unnecessary here — typically just "Recover funds" since the dust/03 retry/park concepts don't apply to close).

### Executor-surface gap (scoped down)

The Executor client (`octora-executor.client.ts`) does not yet expose `buildSwapIx` or any swap CPI wiring (close/04 territory). Rather than block this slice, the close service talks through a typed `CloseOrchestrationAdapter` interface:

```ts
interface CloseOrchestrationAdapter {
  submitWithdrawClose(...): Promise<{ signature; otherSideResidualLamports }>
  submitSwap(...): Promise<{ signature }>
  submitMixerDeposit(...): Promise<{ signature }>
}
```

Production deployments don't pass `closeAdapter` into `createApp`, so `POST /positions/:id/close` rejects with a clear "createCloseService was constructed without an adapter" error. The test harness injects an in-memory adapter to exercise every leg end-to-end. **Wiring this adapter to the real Executor + Mixer clients is explicitly close/04's territory** (the ticket already flags `dlmm_swap` as out-of-scope for close/01 in its "Token-2022 / TransferHook gating" + "Blocked by" sections, though scope-down to the adapter shape is the concrete consequence).

### Other notes

- The close cluster's Recovery Guidance currently surfaces `safeNextStep: contact-support` on all three `*_FAILED` terminals — close/03 will land the user-signed close-recovery action button + drive a permitted transition out of those terminals.
- The dust threshold (`CLOSE_SWAP_DUST_THRESHOLD_LAMPORTS = 1000n`) is a hardcoded named constant in `position.close.service.ts` so future tuning is a one-line change.
- `mixer.deposit` denomination logic (denominate against the original Mixer Pool denomination, remainder stays in stealth) is intentionally pushed down into the `submitMixerDeposit` adapter method — the orchestrator never sees lamport math, only "did the deposit confirm?". The actual denomination resolution lives where mixer wiring lives, not here.
