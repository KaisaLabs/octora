# CU prototype: atomic deposit + addLiquidity

**Status:** ready-for-human
**Type:** enhancement
**Slice:** HITL

## What to build

Prototype an atomic single-transaction flow that combines `mixer.deposit` and Meteora DLMM `add_liquidity` (Position 2 path — deposit then open LP from scratch). Measure compute-unit consumption and transaction size against Solana's limits on a representative DLMM pool.

The output is a **decision**, not a shipped feature: does the atomic path fit within CU + tx-size budget, or do we need to fall back to the two-phase flow?

Note from source design: DLMM `addLiquidity` is CU-heavy. Bin-array init may need to be split into a separate non-fund-moving prep tx (safe to fail).

## Acceptance criteria

- [ ] Working surfpool reproduction of `mixer.deposit + DLMM add_liquidity` as a single signed tx (or single ix bundle)
- [ ] CU and tx-size numbers recorded for at least three representative pools (one tight-range, one wide-range, one with cold bin arrays)
- [ ] Decision recorded as an ADR under `octora-api/docs/adr/` (or `programs/docs/adr/` if on-chain-shaped): atomic single-tx, or two-phase fallback
- [ ] If atomic is infeasible, ADR names the constraint (CU vs tx-size vs bin-array init) so future revisits can target it
- [ ] Findings linked back into this ticket as a comment before closing
