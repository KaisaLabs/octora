# Two-phase deposit→LP state machine + persisted intent

**Status:** ready-for-agent
**Type:** enhancement
**Slice:** AFK

## What to build

Defense-in-depth floor for the **Private Deposit + Position Open** flow. Ship regardless of whether the atomic path (issue 02) is feasible — this is the always-available fallback that guarantees user funds are never truly stuck.

Two phases:

1. `mixer.deposit` confirmed → backend persists `{commitment, intended_pool, denom, expires_at}` keyed by nullifier hash. User holds the nullifier preimage (custodial-less; "stuck" is a UX gap, not a protocol gap).
2. Frontend immediately attempts `withdraw + add_liquidity` (atomic from Stealth Wallet).

State machine (from source design, prototype-confirmed shape):

```
DEPOSITED -> LP_PENDING -> LP_FAILED -> { LP_RETRIED | PARKED | WITHDRAWN }
                       \-> LP_DONE
```

| State | Trigger | UI affordance |
|---|---|---|
| `DEPOSITED` | mixer.deposit confirmed | "Adding liquidity…" |
| `LP_PENDING` | withdraw+addLP submitted | spinner |
| `LP_FAILED` | tx revert / timeout | 3-button panel: retry / park / withdraw |
| `PARKED` | user chose "later" | "Resume in pool" CTA |
| `WITHDRAWN` | user-signed recover | terminal — tx receipt |
| `LP_DONE` | position NFT minted | terminal — position view |

This is an extension of the existing `Position` lifecycle state machine in `octora-api/src/domain/execution-state-machine.ts`. Reconcile vocab — these state names may not match the existing `ExecutionState` union; integration is expected, not a parallel machine.

## Acceptance criteria

- [ ] Persisted intent (`commitment + intended_pool + denom + expires_at`) is stored on `DEPOSITED` and cleared on `LP_DONE` / `WITHDRAWN`
- [ ] State transitions validated by the existing state-machine guard — no other paths allowed
- [ ] `LP_FAILED` UI shows the 3-button panel (retry / park / withdraw) with copy that explains each path's privacy implication
- [ ] `PARKED` resumes correctly via the "Resume in pool" CTA from the user's Position list
- [ ] Integration tests cover: happy path, `LP_FAILED → LP_RETRIED → LP_DONE`, `LP_FAILED → PARKED → LP_RETRIED`, `LP_FAILED → WITHDRAWN`
- [ ] Vocab aligned with the backend glossary — new states either integrate with `ExecutionState` or are explicitly named as a sub-state of `funding-partial`
