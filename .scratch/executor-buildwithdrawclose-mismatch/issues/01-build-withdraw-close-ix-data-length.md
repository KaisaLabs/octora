**Summary:** Test assertion for `buildWithdrawCloseIx` ix-data length omits the Borsh-serialized `Vec<u8>` tail, causing a hard-coded mismatch.

**Current behavior:**
The TS-side test that exercises the executor's withdraw-close instruction builder asserts `ix.data.length === 18`, computed from `8 disc + 4 i32 + 4 i32 + 2 u16`. The actual on-wire length is 26 because the Rust ix takes a trailing `remaining_accounts_info: Vec<u8>` argument that Anchor/Borsh serializes as `4-byte little-endian u32 length prefix + bytes`. The test passes a 4-byte `Buffer` for that argument, so the realized data is `18 + 4 (length prefix) + 4 (content) = 26`.

The Rust ix definition itself is correct. The TS client builder is correct (it forwards the buffer via Anchor's argument serializer). Only the test's hard-coded expectation is wrong.

**Desired behavior:**
The test asserts a length that accounts for the `Vec<u8>` tail. Either:
- Compute the expected length from the actual input buffer's length plus the 4-byte u32 length prefix, OR
- Hard-code the expected length matching the buffer size used in the test (e.g. `8 + 4 + 4 + 2 + 4 + 4 = 26` for the current 4-byte test buffer).

Prefer the first form — it stays correct if the test's buffer size ever changes.

**Key interfaces:**
- The `dlmm_withdraw_close` Rust ix shape: `(from_bin_id: i32, to_bin_id: i32, bps_to_remove: u16, remaining_accounts_info: Vec<u8>)`. This is the source of truth; the test must match its serialization.
- The TS `buildWithdrawCloseIx(WithdrawCloseParams)` client method that wraps the Anchor program client — unchanged.
- Anchor's `Vec<u8>` ABI: `[u32_le length][bytes]`.
