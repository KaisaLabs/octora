Octora — Monorepo → 3-Repo Split Migration Guide

Split the current KaisaLabs/octora monorepo into three independent repos while preserving git history. The current working repo becomes octora-web; octora-api and octora-programs are extracted into new GitHub repos.

Read before doing anything:
  • This is irreversible relative to history rewrites — do not push --force to the existing origin. Always extract into new remotes first, verify, then prune the current repo as the last step.
  • Commit or stash everything first. Current branch is refactor/octora-api with WIP. Do not start a split mid-WIP.
  • Two untracked HTML docs (docs/dust-and-stuck-funds-design.html, docs/trace-linkage-guide.html) — decide which repo owns them before extraction.

Cross-repo coupling that survives the split

  • Program IDs — exist in four places after split: programs/*/src/lib.rs declare_id!, Anchor.toml (programs repo), OCTORA_*_PROGRAM_ID env (api repo), VITE_* env (web repo). Any deploy that changes them now needs a coordinated PR in three repos.
  • IDLs — already vendored as copies in api: octora-api/src/modules/relayer/idl/octora_mixer.json, octora-api/src/modules/execution/clients/idl/octora_executor.json. After split, programs repo publishes them (e.g. into a idl/ dir, GitHub release artifact, or npm package); api repo syncs via a script. Web does not import IDLs directly today, so it is unaffected.
  • Mirrored crypto code — octora-web/src/lib/mixer/{poseidon,merkle-tree,bytes,proof,stealth-wallet}.ts deliberately mirror logic in octora-api/src/modules/{vault,relayer}/.... These are intentional duplicates (browser vs node). Keep them in sync via PR checklist — there is no shared package.
  • Circuits / SRS artifacts — octora-api/src/modules/vault/circuits/ generates artifacts that web consumes at octora-web/public/circuits/. After split, define how the web repo pulls those artifacts (release asset, submodule, or hand-copy + commit).

1. Prerequisites

git filter-repo is the modern, fast replacement for git filter-branch. It preserves history per subdirectory and is what the GitHub docs recommend.

2. Extract octora-api into its own repo

Strategy: clone the monorepo into a throwaway working copy, filter it down to only the octora-api/ subtree (rewriting paths so its contents sit at root), then push to the new remote. The original monorepo is untouched.

2.1 Clone a throwaway copy

cd /tmp
git clone --no-local /Users/theo/Documents/PROJECT/octora octora-api-extract
cd octora-api-extract
# detach from old origin so accidental push can't hit it
git remote remove origin
git remote remove backup 2>/dev/null || true

2.2 Rewrite history to only contain octora-api/, lifted to root

git filter-repo --subdirectory-filter octora-api

After this:

  • Every commit that never touched octora-api/ is gone.
  • Every surviving commit has its paths rewritten so octora-api/src/... becomes src/... at repo root.
  • Branches/tags that contained octora-api changes are kept and re-pointed.

2.3 Sanity-check before pushing

ls                    # should look like: src/ prisma/ api/ infra/ package.json ...
git log --oneline | head -20
git log --oneline --all | wc -l   # roughly: monorepo commit count minus commits that never touched octora-api/

2.4 Push to the new remote

git remote add origin git@github.com:KaisaLabs/octora-api.git
git push -u origin --all
git push     origin --tags

4. Cut a clean octora-web branch from the current repo

octora-web stays in the current checkout. But the current main contains the entire monorepo. To make web the standalone repo, you have two options.

Option A — In-place subtree filter history rewrite on origin

Run filter-repo against the existing checkout to lift octora-web/ to root and drop everything else, then force-push to origin. Simplest, but rewrites public history. Only acceptable because the repo is private and you control all collaborators.

Force-push is destructive. Anyone with an existing clone of KaisaLabs/octora will have to re-clone. Coordinate before doing this. 
cd /Users/theo/Documents/PROJECT/octora

# triple-check WIP is committed or stashed
git status

# 4A.1 — same extraction technique as api, but applied in place
git filter-repo --subdirectory-filter octora-web --force

# 4A.2 — verify
ls   # should now be: src/ public/ index.html package.json vite.config.ts ...

# 4A.3 — push (force, because history was rewritten)
git push origin --all   --force-with-lease
git push origin --tags  --force-with-lease

Option B — Fresh extraction → new remote, then rename recommended

Cleaner. Same workflow as api/programs: extract into a fresh clone, push to a brand-new remote, then on GitHub rename the old octora repo to octora-archive (or delete it) and rename the new repo to octora-web. No force-push, no rewritten origin. 

cd /tmp
git clone --no-local /Users/theo/Documents/PROJECT/octora octora-web-extract
cd octora-web-extract
git remote remove origin
git remote remove backup 2>/dev/null || true

git filter-repo --subdirectory-filter octora-web

# create a TEMPORARY new repo first; rename via GitHub UI after archive
gh repo create KaisaLabs/octora-web-new --private --confirm
git remote add origin git@github.com:KaisaLabs/octora-web-new.git
git push -u origin --all
git push     origin --tags

# Then on GitHub:
#  1. rename KaisaLabs/octora        -> KaisaLabs/octora-archive  (keep as cold backup)
#  2. rename KaisaLabs/octora-web-new -> KaisaLabs/octora-web
Pick one, not both. If you go with Option B, the existing checkout at /Users/theo/Documents/PROJECT/octora is now pointing at an archived remote. Re-clone the new octora-web repo somewhere clean and work from there.

5. Wire up each new repo

5.1 octora-programs

  1. Prune root package.json: keep only Anchor/mocha/ts-mocha/ts-node/typescript/@solana/*/@meteora-ag/dlmm/bn.js/circomlibjs/snarkjs/chai deps and the validator*/test:*/deploy:* scripts. Drop monorepo-only scripts.
  2. Update repository.url in package.json.
  3. Add CI: anchor build + selected mocha suites on PR.
  4. Decide IDL publishing path. Two reasonable options:
    • GitHub Release artifact — every tagged release uploads target/idl/*.json + target/types/*.ts. api consumes via a sync script.
    • Dedicated idl/ dir committed — programs repo commits IDLs after each anchor build; api repo pulls them via a scripts/sync-idl.sh that curls raw GitHub.
  5. Move infra/ here if it contains program deploy infra; otherwise it goes to api.

5.2 octora-api

  1. The repo already has its own package.json, Dockerfile, vercel.json, tsconfig.json, prisma/ — they all sit at root after the subtree filter. Verify nothing in the code imports across former-monorepo paths (e.g. ../programs): the earlier grep showed only comment references, no actual imports.
  2. Replace the vendored IDL files (src/modules/relayer/idl/octora_mixer.json, src/modules/execution/clients/idl/octora_executor.json) with whatever sync mechanism you chose in 5.1.
  3. Update repository.url in package.json.
  4. CI: pnpm typecheck, pnpm test, lint scripts already exist.

5.3 octora-web

  1. vite.config.ts, playwright.config.ts, Tailwind/PostCSS configs sit at root post-extract. Verify.
  2. VITE_OCTORA_API_URL (or whatever the env var is — check .env.example) now points at the deployed octora-api, not a relative dev path.
  3. The browser-side mirrors of api crypto code (src/lib/mixer/*.ts) stay — they are intentional and have no runtime dependency on api.
  4. Define how circuits/SRS artifacts in public/circuits/ get refreshed (release-asset pull, or simply commit them and bump on protocol upgrades).
  5. CI: pnpm typecheck, pnpm test, pnpm test:e2e, pnpm build.

7. Post-split coordination

7.1 Program-ID change checklist

This was a 3-place edit before; after the split it's a 3-repo PR. Update the runbook:

  • octora-programs → programs/octora-executor/src/lib.rs + programs/octora-mixer/src/lib.rs declare_id!; Anchor.toml [programs.*].
  • octora-api → .env / deploy secrets: OCTORA_EXECUTOR_PROGRAM_ID, OCTORA_MIXER_PROGRAM_ID; vendored IDL refresh.
  • octora-web → VITE_* envs; rebuild + redeploy.

7.2 Issue tracker

The .scratch/<feature-slug>/ file-based tracker (per docs/agents/issue-tracker.md) was cross-cutting. After split, each repo has its own. Open issues currently in flight (e.g. production-ix-wiring/02, mentioned in the latest commits) should be assigned to the repo that actually contains the code they touch:

  • close adapters that wire the production executor + mixer ix → octora-api
  • program-side changes → octora-programs
  • UI flows → octora-web

7.3 Memory / context for AI agents

The per-user memory in ~/.claude/projects/-Users-theo-Documents-PROJECT-octora/ is keyed on the current path. After splitting:

  • If you keep working out of /Users/theo/Documents/PROJECT/octora for octora-web, memory continues to apply but now describes only the web scope. Prune entries that no longer apply.
  • If you re-clone to fresh paths for api/programs, you'll get fresh per-project memory dirs. Re-seed them with anything load-bearing (MVP scope, target user, etc.).

8. Local development after split

Three separate clones, three separate pnpm install, three separate dev servers. A suggested local layout:

~/Documents/PROJECT/
  octora-programs/    # anchor build, surfpool, mocha tests
  octora-api/         # pnpm dev  (Fastify on :8787 or whatever)
  octora-web/         # pnpm dev  (Vite on :3000)

Daily flow:

  1. In octora-programs/: anchor build on program changes, then either commit IDLs or upload as release artifact.
  2. In octora-api/: scripts/sync-idl.sh (you'll write this in 5.1), then pnpm dev.
  3. In octora-web/: pnpm dev, point at local api via VITE_OCTORA_API_URL.

9. Rollback

If anything in steps 2–4 looks wrong:

  • The throwaway extraction clones in /tmp can be deleted and redone — they were clones, not in-place.
  • If you already pushed to a new remote and want to redo, delete the GitHub repo and re-run from step 2.1.
  • If you did Option A (in-place force-push) and need to restore, use the bundle from step 1: 
    cd /tmp
git clone /Users/theo/Documents/PROJECT/octora-pre-split.bundle octora-restored
# inspect, then push to a recovery remote if needed
