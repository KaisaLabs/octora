# Octora — Production Readiness & Mainnet Launch Requirements

**Status:** Pre-launch audit · Target: private mainnet beta (no public announcement)
**Last updated:** 2026-05-09
**Scope:** Everything that must be done before real users put real money into Octora on Solana mainnet.

This document is the single source of truth for mainnet-grade readiness. Findings come from a deep audit of:

- `programs/octora-mixer/` — Groth16 ZK mixer (Anchor)
- `programs/octora-executor/` — Meteora DLMM/DAMM CPI wrapper (Anchor)
- `octora-api/` — Fastify backend, relayer, indexer, mixer service
- `octora-web/` — React/Vite frontend
- ZK circuits at `octora-api/src/modules/vault/circuits/`
- Deployment/runbook artifacts at `runbooks/` and `Anchor.toml`

Each item lists: **Severity · File(s) · Problem · Required fix · Estimated effort**.
Effort is rough engineer-hours assuming familiarity with the codebase.

---

## 0. Severity legend

| Tag | Meaning |
| --- | --- |
| **P0 — BLOCKER** | Must be fixed before any mainnet deposit by anyone. Risk: fund loss, full system compromise, or regulatory exposure. |
| **P1 — REQUIRED FOR BETA** | Must be fixed before real users (even invited cohort) deposit. Risk: data loss, abuse, partial fund loss, broken UX in failure modes. |
| **P2 — REQUIRED BEFORE PUBLIC** | Can launch private beta without these, but must be done before opening signups or announcing publicly. |
| **P3 — POST-LAUNCH** | Hardening / nice-to-have. Track in backlog. |

## 1. Smart contract security (P0–P1)

### P0-1 · Permissionless mixer pool initialization
- **File:** `programs/octora-mixer/src/instructions/initialize.rs`
- **Problem:** `initialize` is unguarded — any caller becomes the permanent `pool.authority` (which controls `set_paused`). Code itself flags this as pre-mainnet TODO.
- **Required fix:** Pin the allowed initializer Pubkey via a `require!` against a hardcoded constant, or restrict initialization to the program upgrade authority. Re-deploy mainnet pools only from a known multisig.
- **Effort:** 2h.

### P0-2 · Trusted setup ceremony for Groth16
- **Files:** `programs/octora-mixer/src/verifier/groth16.rs`, `octora-api/src/modules/vault/circuits/withdraw.zkey`, `verification_key.json`
- **Problem:** The verifying key is hardcoded into the program, derived from a `.zkey` file. If that `.zkey` was generated by a single party (`snarkjs zkey new` once, no contributions), that party holds the trapdoor and can mint counterfeit withdrawal proofs at will — drains the entire mixer.
- **Note:** Distribution of `.zkey` (public/circuits) is **correct** — clients need it to prove. The risk is the *origin* of `.zkey`, not its publication.
- **Required fix:** Run a multi-party trusted setup ceremony (Phase 2 of Powers of Tau, e.g. via `snarkjs zkey contribute` with ≥3 independent contributors on independent hardware). Publish ceremony transcript (entropy attestations, hashes per round) to `runbooks/ceremony/`. Re-derive the on-chain verifying key from the final `.zkey`.
- **Effort:** 1–2 days (coordination + transcript publication).

### P0-3 · Recipient/relayer binding in circuit
- **File:** `octora-api/src/modules/vault/circuits/withdraw.circom` (line ~81–86)
- **Problem:** Audit found `recipientSquare <== recipient * recipient` — a square is not a binding constraint. Recipient is enforced *on-chain* by `withdraw.rs` via `pubkey_to_field_hash`, so the program is safe today, but the circuit is structurally weak: any tooling that trusts the proof alone (e.g. an off-chain relayer's pre-flight) is fooled. This is also what auditors will flag first.
- **Required fix:** Bind recipient and relayer addresses into the circuit's hash inputs (e.g. include them in the Poseidon hash whose output is a public input). Re-compile circuit, re-run trusted setup (P0-2 captures this), regenerate verifying key bytes for `groth16.rs`.
- **Effort:** 4–8h (circuit edit + tests) + ceremony.

### P0-4 · Missing signer constraints on DAMM instructions
- **Files:** `programs/octora-executor/src/instructions/damm/{init,deposit,withdraw}.rs`
- **Problem:** Only `damm/claim_fees.rs` declares `stealth: Signer`. The other three accept `stealth: AccountInfo` (or equivalent without `Signer`). On Solana this means the transaction does not need to be signed by the stealth keypair to invoke these instructions. Consequence ranges from nuisance griefing (someone else funds your PDA) to severe (an attacker drains rent or mis-routes liquidity) depending on what's downstream. Either way, every authority gate must hold.
- **Required fix:** Change to `stealth: Signer<'info>` on `damm_init`, `damm_deposit`, `damm_withdraw` (and any other instruction in either program where `stealth` is the authoritative actor). Add an integration test that submits the instruction without the stealth signature and asserts failure.
- **Effort:** 2h + tests.

### P0-5 · Executor pause mechanism
- **Files:** `programs/octora-executor/src/lib.rs`, new `instructions/admin_pause.rs`
- **Problem:** `octora-mixer` has `set_paused`; `octora-executor` does not. If a DLMM/DAMM CPI bug or upstream Meteora bug surfaces after launch, you can halt deposits but not LP execution.
- **Required fix:** Add `Config` PDA with `paused: bool` and `authority: Pubkey` to executor; add `set_paused` instruction (authority-gated, using same multisig as mixer); add `require!(!config.paused, ExecutorError::Paused)` to every state-mutating instruction.
- **Effort:** 4h + tests.

### P0-6 · Anchor.toml has no `[programs.mainnet]`
- **File:** `Anchor.toml`
- **Problem:** Only devnet and localnet program IDs are defined. Mainnet IDs aren't pinned, so build/IDL/anchor-client tooling has no canonical mainnet binding.
- **Required fix:** After deploying programs to mainnet (with a fresh, never-used keypair), add:
  ```toml
  [programs.mainnet]
  octora_executor = "<MAINNET_PROGRAM_ID>"
  octora_mixer    = "<MAINNET_PROGRAM_ID>"
  ```
  Commit the program-id keypairs to a sealed offline store (NOT the repo).
- **Effort:** 30min + deploy.

### P1-7 · Upgrade authority should be a multisig from day 1
- **Tooling:** Squads v3 (Solana standard) or equivalent.
- **Problem:** Default Anchor deploy puts the program under a single key's BPF Upgrade Authority. That key, if compromised, lets an attacker swap the program binary and drain the mixer.
- **Required fix:** After mainnet deploy, run `solana program set-upgrade-authority <PROGRAM_ID> --new-upgrade-authority <SQUADS_VAULT_PDA>` for both programs. 2-of-3 minimum for beta; 3-of-5 before public launch. Document signers in `runbooks/deployment/upgrade-authority.md`.
- **Effort:** 2h + Squads setup.

### P1-8 · Cargo release profile lacks `overflow-checks`
- **Files:** `Cargo.toml` (workspace) and `programs/*/Cargo.toml`
- **Problem:** Solana programs in release mode default to wrapping arithmetic. Any untested arithmetic path becomes a silent overflow vulnerability.
- **Required fix:** Add to workspace `Cargo.toml`:
  ```toml
  [profile.release]
  overflow-checks = true
  ```
- **Effort:** 5min.

### P1-9 · Verifiable build setup
- **Tooling:** `solana-verify` (formerly Otter).
- **Problem:** Without verifiable builds, users (and you) cannot prove the on-chain bytecode matches the source in this repo. For a privacy product where trust is the value proposition, this matters.
- **Required fix:** Add Docker-based reproducible build. Document in `runbooks/deployment/verify.md` how anyone can run `solana-verify verify-from-repo <repo-url>` and get a match.
- **Effort:** 4h.

### P1-10 · Root history window
- **File:** `programs/octora-mixer/src/constants.rs` (`ROOT_HISTORY_SIZE = 30`)
- **Problem:** ~12 seconds of root validity at mainnet slot times. Users who deposit then take >12s to fetch state and prove will hit `RootNotFound`. Worse — privacy is improved by *waiting longer* between deposit and withdraw, which this constant penalizes.
- **Required fix:** Raise to `256` (≈100s) or `1024` (≈7min). Each root is 32 bytes, so 1024 = 32KB, well within account size budget. Reassess with realistic prover latency under load.
- **Effort:** 30min + account-size review.

### P1-11 · CPI signer re-pinning audit on DAMM path
- **Files:** `programs/octora-executor/src/instructions/damm/*.rs`
- **Problem:** DLMM instructions correctly re-pin the PoolAuthority PDA into the CPI account list (see `// Fix #4: CPI signer re-pinning` comments). The DAMM instructions need verification that the same mitigation is applied.
- **Required fix:** Audit each DAMM instruction (`init`, `deposit`, `withdraw`, `claim_fees`) and apply the same re-pinning pattern. Add LiteSVM test cases that try the substitution attack.
- **Effort:** 4h.

### P2-12 · IDL on-chain publication
- **Problem:** Anchor IDLs published on-chain let any client decode without a copy of the IDL JSON. Improves third-party tooling and verifies the program matches expectations.
- **Required fix:** `anchor idl init <PROGRAM_ID> --filepath <idl.json>` post-deploy.
- **Effort:** 30min.

## 2. Privacy guarantees (P0–P1)

### P0-13 · Trusted setup ceremony — covered above in P0-2

### P0-14 · Per-deposit single denomination already enforced; document it
- **File:** `programs/octora-mixer/src/instructions/deposit.rs`
- **Status:** Code correctly rejects mismatched denominations at deposit time. Good.
- **Required fix:** Document publicly which denominations are supported on mainnet. Mixing across denominations is the #1 user-facing privacy footgun. Provide UI guidance.
- **Effort:** writing only.

### P0-15 · Privacy delay must persist across relayer restart
- **File:** `octora-api/src/modules/relayer/relayer.service.ts:36–58`
- **Problem:** `rootFirstSeenAt` is an in-memory `Map`. Relayer restart resets it, so a user can deposit, restart the relayer, and withdraw immediately — the timing-correlation defense disappears.
- **Required fix:** Persist `(root, first_seen_slot)` to PostgreSQL via a new `MixerRootSeen` Prisma model. On startup, read the table; on every observation, upsert. Use **slot height**, not wall-clock time, as the gate (slot height comes from `getSlot()` on the RPC and is monotonic).
- **Effort:** 4h (Prisma migration + repo + service edit + tests).

### P0-16 · Stealth wallet encryption derivation is deterministic
- **File:** `octora-api/src/modules/relayer/stealth-wallet.ts:52–112`
- **Problem:** HKDF salt and info are static constants. Same user signing the same message twice → same encryption key → identical ciphertext blobs cluster across deposits, linking the user's identity to multiple stealth wallets.
- **Required fix:** Include a per-stealth random nonce in the HKDF `info` parameter, store it alongside the ciphertext (it's not secret). Migrate the v2 → v3 encryption format. Document migration path for any test data.
- **Effort:** 4h.

### P1-17 · Relayer learns recipient (inherent, but document it)
- **File:** `octora-api/src/modules/relayer/relayer.service.ts:131–157`
- **Problem:** Relayer sees: nullifier hash, recipient address, fee, root. This is inherent to relayer-mediated mixers. Compromise of the relayer → linkability for any in-flight withdrawal.
- **Required fix:** (a) Operationally: minimize relayer log retention to <24h, encrypt at rest. (b) Long-term: support user-submitted withdrawals (no relayer) for users who hold gas. (c) Document this clearly in `runbooks/PRIVACY_MODEL.md`.
- **Effort:** 4h doc + retention setup.

### P1-18 · No batching of withdrawals
- **Problem:** A 1:1 deposit→withdraw on a low-traffic pool is statistically linkable by amount + timing. Until the anonymity set is healthy (>~50 active deposits), every withdrawal is near-trivially de-anonymized.
- **Required fix:** During private beta, enforce a minimum N depositors before any withdraw is processed (`MIN_ANONYMITY_SET=20`). Or: socially coordinate "deposit waves" with the beta cohort.
- **Effort:** 2h logic + UX warning.

### P2-19 · MEV / sandwich on add_liquidity
- **Files:** `programs/octora-executor/src/instructions/dlmm/add_liquidity.rs`
- **Problem:** Slippage protection on DLMM bin entry. Confirm `min_out` / `max_active_id` parameters are exposed to user and not hardcoded.
- **Required fix:** Audit slippage params, expose to UI, default to 0.5% on stable pairs / 1% on volatile, allow override.
- **Effort:** 2h.

## 3. Backend — `octora-api` (P0–P2)

### P0-20 · No wallet-signature auth on mutating endpoints
- **Files:** `octora-api/src/modules/positions/position.routes.ts`, `position.controller.ts`
- **Problem:** `POST /positions/intents`, `/execute`, `/claim`, `/withdraw-close` have no signature gate. Any caller can act as any wallet. The `signedMessage` field exists on `ExecuteIntentBody` but isn't cryptographically verified.
- **Required fix:** Add `requireWalletSignature` Fastify preHandler that:
  1. Accepts headers `x-wallet-address`, `x-signed-nonce`, `x-signature`.
  2. Verifies `nacl.sign.detached.verify(nonce, signature, walletAddress)`.
  3. Persists nonce in a 5-min `AuthNonce` table to prevent replay (one-time use).
  4. Asserts `walletAddress` matches the intent's `walletAddress` field.
- **Effort:** 4–6h including tests.

### P0-21 · Relayer hot wallet keypair on disk
- **Files:** `octora-api/src/modules/relayer/relayer.routes.ts:37–38`, `octora-api/src/common/config.ts` (`mixerRelayerKeypairPath`, `executorRelayerKeypairPath`)
- **Problem:** Single JSON file on the API host. Server compromise = full key compromise. No rotation, no segregation between mixer-fee wallet and executor-funding wallet.
- **Required fix (private beta minimum):**
  1. Move keys off API host entirely. Run a separate signing service on a hardened VM (or HSM via AWS KMS / GCP Cloud HSM). API calls signing service over mTLS.
  2. Keep mixer-fee wallet (small float, ≤$500) and executor wallet separate.
  3. CloudWatch alarm: balance change >$X within Y minutes → page.
  4. Document key-rotation runbook (rotate every 30 days during beta).
- **Required fix (long-term):** Migrate to Squads or Fireblocks for relayer treasury; use ephemeral derived keys per-request.
- **Effort:** 1–2 days for KMS-backed signer + alarms.

### P0-22 · CORS wildcard fallback
- **File:** `octora-api/src/common/config.ts:46` — `frontendUrl: process.env.FRONTEND_URL ?? "*"`
- **Problem:** If `FRONTEND_URL` env is unset in production, any origin can call the API on behalf of an authenticated browser.
- **Required fix:** Make `FRONTEND_URL` required. Throw at startup if missing in `NODE_ENV=production`. Use a strict allowlist (comma-separated list of expected origins).
- **Effort:** 30min.

### P0-23 · Health endpoint is fake
- **File:** `octora-api/src/app.ts:104` — `app.get('/health', async () => ({ ok: true }))`
- **Problem:** Always 200. Load balancers / orchestrators won't catch DB down, RPC down, relayer keypair missing, mixer paused.
- **Required fix:** Real `/health` that checks: (a) `prisma.$queryRaw'SELECT 1'`, (b) `connection.getSlot()` returns within 2s, (c) relayer keypair file exists and decrypts, (d) `mixer.config.paused === false`. Return JSON `{db, rpc, relayer, mixer}` with overall status. 503 on any failure.
- **Effort:** 1h.

### P1-24 · Rate limiting not wired up
- **Files:** `octora-api/src/modules/mixer/rate-limit.ts` (exists), `octora-api/src/modules/{positions,relayer,mixer}/*.routes.ts` (don't use it)
- **Problem:** Audit found rate-limit module exists but isn't applied to any route.
- **Required fix:** Apply `@fastify/rate-limit` to:
  - `POST /positions/intents` — 10/min/IP, 30/hour/wallet
  - `POST /positions/:id/execute` — 5/min/wallet
  - `POST /positions/:id/claim`, `/withdraw-close` — 5/min/wallet
  - `POST /relayer/withdraw` — 5/min/IP, 20/hour/IP
  - `POST /mixer/deposit-tx` — 10/min/IP
- **Effort:** 2h.

### P1-25 · Beta access gating not enforced
- **Files:** `octora-api/src/modules/waitlist/`, `position.service.ts`
- **Problem:** Waitlist signups are collected but `waitlistRepo.isApproved(walletAddress)` is never called from the position-creation path or mixer routes.
- **Required fix:** Add `assertBetaAccess(wallet)` middleware at the top of every mutating handler. Add admin endpoint `POST /admin/waitlist/approve` (gated by an admin token in env) to flip `approved` flag.
- **Effort:** 3h.

### P1-26 · Per-position and global TVL caps
- **Files:** `octora-api/src/modules/positions/position.service.ts`, mixer service
- **Problem:** No caps. A bug or attacker can cause unbounded fund concentration at risk.
- **Required fix:**
  - `MAX_POSITION_USD` (config: $500 for beta)
  - `MAX_GLOBAL_TVL_USD` (config: $25,000 for beta)
  - `MAX_POSITIONS_PER_WALLET` (config: 5 for beta)
  - Reject intent creation when caps exceeded; clear error message.
- **Effort:** 2h.

### P1-27 · Blockhash expiry / retry logic missing
- **Files:** `octora-api/src/modules/mixer/mixer.service.ts:119`, `octora-api/src/modules/relayer/relayer.service.ts:334`
- **Problem:** No retry on `BlockhashNotFound`. Under congestion, transactions silently fail.
- **Required fix:** Wrap `sendAndConfirm` in retry helper: max 3 attempts, fresh blockhash + recompute signers on each retry, exponential backoff. Distinguish retryable (`BlockhashNotFound`, `NodeUnhealthy`) from terminal errors.
- **Effort:** 3h + tests.

### P1-28 · Compute budget and priority fees are static
- **Files:** mixer.service.ts:117, relayer.service.ts:331
- **Problem:** Hardcoded `setComputeUnitLimit({ units: 400_000 })` and no `setComputeUnitPrice`. On a busy mainnet, transactions won't land.
- **Required fix:**
  - Profile actual CU usage with `simulateTransaction` and set limit to `cu_used * 1.2`.
  - Fetch recent priority fees via `connection.getRecentPrioritizationFees([accounts])` and set price to 75th percentile.
  - Cap maximum priority fee to a sane upper bound (e.g. 0.01 SOL) to prevent fee griefing.
- **Effort:** 4h.

### P1-29 · Recovery worker for stuck positions
- **Files:** `octora-api/src/domain/state-machine.ts`, `octora-api/src/modules/indexer/indexer.service.ts`
- **Problem:** State machine has 7 failure stages; recovery is "manual" per README. No worker reconciles stuck positions.
- **Required fix:** Background job (every 30s):
  1. Find positions in `executing_on_meteora` for >5min → check signature status → advance or fail.
  2. Find positions in `indexing` for >2min → re-fetch on-chain state → advance.
  3. Emit alert (Sentry) on positions in `failed` stage.
- **Effort:** 1 day.

### P1-30 · Structured logging + Sentry
- **Files:** `octora-api/src/app.ts:81–97`, package.json
- **Problem:** Pino is installed but emits unstructured to stdout; errors are `console.error`. No Sentry.
- **Required fix:**
  - Configure Pino with JSON output, ISO timestamps, request ID propagation.
  - Wire `@sentry/node` with traces; tag transactions by route.
  - PII redaction: strip `signedMessage`, `signature`, full `Authorization` headers.
  - Never log: keypair paths, decrypted secrets, full nullifiers (truncate to 8 chars).
- **Effort:** 4h.

### P2-31 · Database indexes for production queries
- **File:** `octora-api/prisma/schema.prisma`
- **Required fix:** Audit indexes for the queries the API actually runs. At minimum: `Position.walletAddress`, `Position.status`, `Activity.positionId`, `MixerRootSeen.root`. Run `EXPLAIN ANALYZE` on top-10 query patterns.
- **Effort:** 3h.

### P2-32 · Database backups + WAL archival
- **Files:** `octora-api/infra/docker-compose.dev.yml` (only dev exists)
- **Required fix:** Production deployment uses managed Postgres (RDS / Supabase / Neon) with point-in-time recovery enabled. If self-hosted: WAL archiving to S3 every 5min, daily full backup, weekly restore drill.
- **Effort:** 1 day setup, ongoing ops.

### P2-33 · OFAC / sanctions screening (regulatory, not optional)
- **Problem:** A privacy mixer that does no screening exposes the operator to massive legal risk in US/EU jurisdictions (Tornado Cash precedent). Even if you decide not to screen, the decision and rationale must be documented.
- **Required fix:** At minimum: integrate Chainalysis Address Screening or TRM Labs API at deposit-side. Reject deposits from sanctioned addresses with a clear error. Log decisions for audit trail. If skipping, get a written legal opinion and document the corporate structure of the operator (offshore, no US users, etc.).
- **Effort:** 1 day integration; weeks for legal opinion.

## 4. Frontend — `octora-web` (P1–P2)

### P1-34 · Default cluster is devnet
- **File:** `octora-web/src/lib/solana/config.ts:13` — `DEFAULT_CLUSTER: "devnet"`
- **Required fix:** Drive from `VITE_NETWORK`. Fail at build if unset for prod build. Add `import.meta.env` validator.
- **Effort:** 1h.

### P1-35 · Network mismatch detection + warning banner
- **File:** `octora-web/src/providers/SolanaProvider.tsx`
- **Problem:** User on devnet wallet can connect to mainnet frontend silently.
- **Required fix:** On wallet connect, fetch `getGenesisHash()` from connection vs from wallet's RPC. If mismatch → block mutating actions and show banner "Wallet on <X>, app on <Y>. Switch network to continue."
- **Effort:** 3h.

### P1-36 · Beta + UNAUDITED warning UX
- **Required fix:**
  - Persistent top banner: "BETA — UNAUDITED — DO NOT DEPOSIT FUNDS YOU CAN'T AFFORD TO LOSE"
  - First-deposit modal: scrollable risk disclosure + checkbox + signed-acknowledgement (signMessage with ToS hash).
  - Persist `acknowledgedTosVersion` per wallet in DB.
- **Effort:** 4h.

### P1-37 · Error boundaries + production loading/empty states
- **Required fix:** Top-level React error boundary that captures and reports to Sentry. Per-page boundaries for `/pools`, `/portfolio`, `/positions/:id`. Skeleton loaders for all data fetches; explicit empty states (no positions yet, no pools matched).
- **Effort:** 1 day.

### P1-38 · Stealth wallet UX is high-risk
- **Files:** `octora-web/src/lib/stealthVault.ts`
- **Problem:** Users may not understand the stealth wallet is ephemeral, that losing access = losing funds (rent + any unwithdrawn dust), and that signing the same vault-derivation message in another browser is the only recovery.
- **Required fix:** Pre-deposit modal explaining stealth wallet model. Recovery flow tested and documented. "Export stealth wallet seed" button so users hold their own backup.
- **Effort:** 1 day.

### P1-39 · Frontend remove all dev-only mock data on prod build
- **Files:** `octora-web/src/data/`, audit any `import.meta.env.DEV` branches
- **Required fix:** Tree-shake mock data from prod bundle. Add CI check that `npm run build` doesn't include strings like `MOCK_`, `DEMO_`.
- **Effort:** 2h.

### P2-40 · Bundle size + CSP
- **Required fix:** Strict CSP headers (no `unsafe-inline`, no `unsafe-eval` — note: ZK proving via wasm needs `wasm-unsafe-eval`). SRI hashes on any external scripts. Audit bundle for unused deps.
- **Effort:** 4h.

## 5. Infrastructure & operations (P1–P2)

### P1-41 · Production deployment story
- **Required deliverables:**
  - `infra/docker-compose.prod.yml` — API + Postgres + signing service.
  - `Dockerfile` for `octora-api` — multistage, non-root user, distroless or alpine.
  - Cloud target: a single VM (Hetzner / Fly.io / Render) is fine for private beta. Document IP allowlist for admin endpoints.
  - SSL: Caddy or Let's Encrypt + nginx.
  - Static frontend: Vercel / Netlify / Cloudflare Pages with the API URL injected at build time.
- **Effort:** 1–2 days.

### P1-42 · CI/CD
- **Required fix:** GitHub Actions:
  - On PR: lint, typecheck, `pnpm test`, `anchor build`, `cargo test`, prisma migration drift check.
  - On main merge: build + push Docker image, deploy to staging.
  - Manual approval gate → mainnet deploy.
- **Effort:** 1 day.

### P1-43 · Secrets management
- **Required fix:** No `.env` files in production. Use Doppler / 1Password Secrets / AWS Secrets Manager / Fly.io secrets. Rotate every 30 days during beta.
- **Effort:** 4h.

### P1-44 · Monitoring + alerting baseline
- **Required minimums:**
  - **Sentry** — backend + frontend errors.
  - **UptimeRobot / Better Uptime** — `/health` every 60s, alert on 2 consecutive failures.
  - **Custom metrics:** mixer TVL, relayer wallet balance, position state distribution, withdrawal success rate.
  - **PagerDuty / OpsGenie** — for critical alerts (relayer balance < threshold, health failure, position stuck >10min).
- **Effort:** 1 day.

### P1-45 · Incident response runbooks
- **Files:** create `runbooks/incident/`
- **Required runbooks:**
  - `mixer-pause.md` — how to pause/unpause; who approves.
  - `relayer-key-rotation.md` — step-by-step.
  - `stuck-position-recovery.md` — by failure stage.
  - `program-bug-response.md` — emergency upgrade procedure with multisig.
  - `database-restore.md` — tested restore from backup.
- **Effort:** 1 day.

### P2-46 · Public RPC will fail
- **Required fix:** Procure dedicated mainnet RPC (Helius Premium, Triton, QuickNode). Configure separate endpoints for: relayer (write-heavy, low-latency), indexer (read-heavy, high TPS), public web (CDN-cached, low-priority).
- **Effort:** 2h once contract is signed.

### P2-47 · Indexer reorg handling
- **File:** `octora-api/src/modules/indexer/indexer.service.ts`
- **Problem:** Solana mainnet has occasional rollbacks. Position state advanced on `confirmed` slot can be reverted.
- **Required fix:** Indexer should consume `finalized` commitment for state transitions. `confirmed` only for UX optimism. On detected reorg, rollback affected positions.
- **Effort:** 1 day.

## 6. Testing (P1–P2)

### P1-48 · Anchor program integration tests in CI
- **Files:** `tests/`, `Anchor.toml:24`
- **Problem:** Tests exist but `anchor test` is not part of CI; coverage unknown.
- **Required fix:**
  - Add LiteSVM or Bankrun fixtures for both programs.
  - Test cases per audit finding (e.g. signer-missing on DAMM, CPI substitution attack, replay).
  - GitHub Actions runs `anchor test` on every PR with mainnet-cloned fixture accounts.
- **Effort:** 2 days.

### P1-49 · End-to-end test: deposit → withdraw on devnet
- **Required fix:** Single Playwright test that runs the full flow on devnet using a fresh wallet. Run nightly. Failure pages on-call.
